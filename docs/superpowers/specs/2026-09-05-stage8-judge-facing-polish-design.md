# Stage 8 Judge-Facing Polish Design

## Goal

Make the existing ClubTreasury AI workflow easier to prove, explain, and safely demo without changing its core custody or human-control boundaries.

The final judge story is:

**Natural language / receipt image → Gemini structures evidence → deterministic rules validate → human decides → Sui executes → blockchain proof is visible.**

## Scope

This change includes seven coordinated improvements:

1. Gemini-assisted budget generation.
2. Visible Gemini provenance and AI audit indicators.
3. Stronger Sui on-chain proof links and payout evidence.
4. Reusable architecture badges for AI → Rules → Human → Sui.
5. A judge-friendly System Status page backed by the existing health endpoint.
6. A focused Supabase/application security review and only necessary hardening changes.
7. A final Playwright golden-path smoke test using mocked external wallet/chain edges in CI.

No new token support, DAO voting, notification system, mobile app, or automatic payout behavior is added.

## 1. Gemini Budget Generation

### Existing capability

`src/lib/ai/gemini.ts` already implements `parseBudget(input)` using Google Gemini structured JSON output. The Budget page currently bypasses this and only supports manual category editing.

### New flow

Add a live-only Gemini assistant section to the existing `BudgetBuilder`.

The treasurer can type a natural-language instruction such as:

> I have 10 USDC. Use 4 for food, 3 for marketing, 2 for transport and 1 for miscellaneous.

The client calls a new server route, `POST /api/ai/budget-draft`, which:

- requires an authenticated, verified wallet session;
- requires live Gemini configuration;
- calls the existing `getAIService().parseBudget()` path;
- returns a structured draft and safe provenance metadata;
- never writes budget data to Supabase.

The client then replaces or previews the editable category rows with the generated draft.

A human must still click **Confirm budget**. The existing deterministic total check remains authoritative and the existing `/api/treasuries/[treasuryId]/budget` persistence route remains the only write path.

### Failure behavior

- Gemini unavailable → show a clear error and keep manual entry available.
- Invalid/ambiguous Gemini result → display notes and do not auto-confirm.
- Budget locked by Sui activation → disable Gemini generation and manual editing.
- Generated total does not equal the treasury total → deterministic preview remains `under_allocated` or `over_allocated`; confirmation stays blocked.

## 2. AI Provenance and Audit Indicators

Introduce a small reusable provenance model and component, not a second AI subsystem.

Visible fields may include:

- Provider: Google Gemini
- Model: configured Gemini model
- Mode: Live
- Task: Budget draft / Receipt analysis
- Generated at: server timestamp
- Human confirmation required

Never expose API keys, prompts containing secrets, or raw authentication data.

### Receipt analysis

The existing claim review already displays stored Gemini-extracted fields. Add a compact provenance header above that panel so judges can see that the extraction is live Gemini-backed rather than sample UI.

### Budget draft

The generated draft panel shows the same provenance information and a label such as **Generated by Gemini · Review before confirming**.

### Persistence

For receipt analysis, add non-sensitive AI metadata to the persisted claim audit surface if schema changes are low-risk. Preferred shape:

- `ai_provider`
- `ai_model`
- `ai_task`
- `ai_generated_at`
- `ai_status`

If schema risk is higher than benefit, preserve the existing receipt result and expose provenance from server configuration without pretending historical metadata was persisted. The implementation must be explicit about which metadata is persisted versus runtime-only.

For budget generation, the draft is advisory and is not persisted as an approved budget until the human confirms it. No separate permanent AI draft table is required.

## 3. Better Sui On-Chain Proof

The existing History page already links to the explorer. Strengthen that presentation instead of inventing a new proof source.

Each confirmed payout card should clearly show:

- Amount
- Recipient
- Treasury/event
- Category
- Transaction digest
- Confirmed timestamp
- Sui Testnet status label
- A primary **View on SuiVision** / **Open explorer proof** action

Add explanatory copy:

**Treasurer signed → Treasury paid → Member received**

Where the existing history API already has the necessary values, display them directly. Do not claim balance-change verification unless the app has actually verified that evidence server-side.

The payout panel should also provide the explorer link immediately after finality is confirmed.

## 4. Architecture Badges

Create one reusable component for four system-boundary badges:

- Gemini AI
- Deterministic Rule
- Human Decision
- Sui On-chain

Use these in:

- Budget generation section
- Claim review
- Claim payout / paid state
- System Status page

The claim review should visually reinforce the pipeline:

Gemini extraction → deterministic checks → human decision → Sui payout

These badges are explanatory only; they must not change authorization or business logic.

## 5. System Status Page

Add `/dashboard/status` and a navigation entry called **System**.

The page calls the existing `/api/health` endpoint and renders safe readiness data:

- Gemini: Live / Mock / unavailable
- Gemini live requests enabled
- Gemini API key configured: yes/no only
- Supabase claim mode and configured status
- Sui network
- Move package configured
- Overall readiness

Add the configured Gemini model name to the health response because that is non-secret and useful for provenance.

The page must never display:

- Gemini API key
- Supabase secret key
- wallet private keys
- database passwords
- auth tokens

## 6. Security Review and Hardening

Perform a focused review of the touched and adjacent production boundaries:

- Supabase RLS policies on claims, treasuries, budget categories, memberships, payment attempts, receipt storage, and activation tables.
- RPC execute permissions for security-definer functions.
- Member versus treasurer authorization on claim submission and decision APIs.
- Server-only handling of Gemini and Supabase secret keys.
- Receipt preview authorization.
- Payment snapshot immutability and duplicate-payout protections.
- No client-side ability to change approved amount, recipient, treasury, category, or currency before payout.

Use Supabase security advisors as evidence, but do not blindly change intentional security-definer RPCs that already enforce internal authorization. Any hardening change must include a regression test and preserve the live smoke-tested workflow.

No production migration is applied automatically as part of the feature branch. If a new migration is required, it must be forward-only and reviewed separately before production application.

## 7. Final E2E Golden Path

Extend Playwright with a judge-facing golden path using deterministic mocks for external systems while exercising real application routes/components.

The automated path should cover:

1. Treasurer sees live/system-ready presentation in the mocked environment.
2. Gemini budget draft request returns a structured draft.
3. Generated categories populate the editable budget.
4. Deterministic total validation blocks invalid totals and permits exact totals.
5. Human confirms the budget.
6. Member claim submission path remains separate from treasurer review.
7. Receipt AI provenance is shown on review.
8. Treasurer approval results in approved-unpaid, never automatic paid.
9. Payout UI requires an explicit wallet-signature step.
10. Confirmed payout displays Sui proof and explorer link.

Real Sui wallet signatures and Testnet transfers remain manual smoke-test gates and are not executed by CI.

## Data and API Changes

Expected additions:

- `POST /api/ai/budget-draft`
- safe AI provenance response type
- optional non-sensitive receipt AI metadata fields if schema review confirms low risk
- `/dashboard/status`
- `GEMINI_MODEL` surfaced through `/api/health`

Existing write paths remain unchanged for approved budget and payment state.

## UI Design

Keep the current ClubTreasury visual system. No redesign.

New UI should use the existing rounded-card, violet AI accent, emerald safety/confirmed accent, and dark green human-control panels.

Gemini draft must always appear as an editable proposal, never as an automatically accepted budget.

## Safety Boundaries

The implementation must preserve all of these:

- Gemini never approves claims.
- Gemini never writes an approved budget without a human confirmation click.
- Gemini never signs or broadcasts a transaction.
- Claim approval and payment remain separate.
- The member cannot access treasurer decision or payout actions.
- Payment uses the immutable approved snapshot.
- Sui wallet signature remains explicit.
- Production failures must fail safe to manual review/reconciliation rather than hidden mock behavior.

## Testing Strategy

Use TDD for each behavioral change.

Required checks before merge:

- Unit tests for budget-draft route/service and provenance formatting.
- Unit tests for health/status model.
- Existing unit suite passes.
- Typecheck passes.
- Lint passes.
- Production build passes.
- Playwright smoke passes including the new golden path.
- Security advisor results reviewed and documented.

## Delivery Strategy

Implement on `stage8/judge-facing-polish` and open one focused PR after the spec is approved.

Do not merge automatically. Do not apply any new production Supabase migration automatically. After CI is green, perform one manual production smoke test covering:

Gemini budget draft → human budget confirmation → member claim → Gemini receipt extraction → human approval → explicit Sui payout → explorer proof → live dashboard/history update.
